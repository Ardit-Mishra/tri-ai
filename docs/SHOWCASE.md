# Tri-AI Showcase

## What the public demo demonstrates

The hosted dashboard is a **simulation**, not a remote control panel. It makes
the system legible without exposing the operator's actual work:

1. A request is framed into a bounded brief.
2. Research and planning produce retained evidence and acceptance checks.
3. A builder prepares a release candidate in an isolated workspace.
4. A verifier evaluates the candidate against explicit checks.
5. A release packet waits for a human decision; it never publishes itself.

The 3D brain is not a claim that Tri-AI has consciousness. It is an interactive
map of the durable context that an execution system needs: task state, accepted
rules, evidence, available capabilities, and candidates awaiting evaluation.
Neural signals represent data moving through that graph. They are deliberately
bounded and can be paused or replaced by the accessible 2D view.

## How to discuss it in an interview

Start with the tension Tri-AI is built around: an agent can describe successful
work even when the work is wrong. The response is not more agent theatre. It is
a task contract with a command that decides whether the result is accepted.

Then open the demo and point to three things:

- **Execution topology:** specialist work is decomposed, connected, and
  inspectable rather than hidden behind one chat transcript.
- **Brain inbox:** durable context has source, trust, and scope; it cannot
  silently become a policy or deployment decision.
- **Release gate:** a passing verification result creates a reviewable release
  decision. The system does not push, deploy, or alter public infrastructure
  without a person approving that action.

## Honest boundary

The public demo runs only the prebuilt scenario. The real local runtime is not
connected to the hosted service. The system's ability to run work depends on a
task-specific verifier; where no meaningful verifier exists, Tri-AI should
prepare evidence for human review rather than claim autonomy.
